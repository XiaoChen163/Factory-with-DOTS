# A01：统一生命、伤害与归零处置实施计划

日期：2026-11-11。状态：待实施。

本计划细化 [Future-Plan-2](Future-Plan-2.md) 中 A01 的生命与伤害契约，为 A03 的受伤/死亡、A04 的枪械命中、B01 的建筑瘫痪与维修提供统一接口。文档完成不代表上述功能已实现或 A01 已通过验收。

## 1. 目标与边界

1. 玩家、敌人、机器人、建筑共用同一套生命、伤害与回复规则。
2. 统一血量写入方；其他系统通过请求协作，不直接扣血、加血或触发复活。
3. 区分伤害来源定义、一次伤害请求、正式结算结果和表现事件。
4. 通过归零处置策略及实体已有组件组合，实现死亡、瘫痪等不同结果。
5. **本计划内所有请求和所有生命归零后果，均在各自产生后的下一模拟 Tick 生效，不在产生当 Tick 立即生效。**
6. 遵循现有 ECS、物理、库存、内容工具和表现桥接，不建立第二套库存或角色控制框架。
7. **生命、伤害和回复数值统一使用 `int`；正式结算不使用浮点数，也不在每次结算时临时将浮点值强制转换为整数。**

A01 首先交付数据契约、时序、校验与可测试的基础结算。完整玩家死亡/重生接入属于 A03，射击和命中请求生成属于 A04，建筑维修与停机恢复属于 B01。相关阶段逐步接入同一协议，不提前制作完整战斗系统。

本轮计划不要求护甲、护盾、暴击、穿透、复杂抗性、持续效果叠层、肢体损伤、多人同步或通用效果编辑器。基础伤害类型保留明确枚举入口，初始可以仅支持动能；增加类型不自动意味着已经实现对应抗性规则。

## 2. 强制时序：请求与归零后果各延迟一个 Tick

### 2.1 Tick 定义与统一阶段

Tick 指 `FixedStepSimulationSystemGroup` 的一次正式模拟步，不是一次渲染帧，也不是一次 Editor Update。项目当前固定频率为 `FactorySimulationTime.TicksPerSecond = 60`。

每个 Tick K 按以下逻辑阶段执行：

| 阶段 | 职责 |
|---|---|
| K 的起始提交阶段 | 提交上一 Tick 产生、到 K 到期的归零/恢复状态转换和正式后果；再结算上一 Tick 产生、到 K 到期的伤害/回复等请求 |
| K 的正常模拟阶段 | 移动、物理查询、单位决策、生产等读取已经提交的正式状态；产生的新请求只写入下一 Tick 队列 |
| K 的输出阶段 | 导出已提交状态、请求结果和已生效事件；本 Tick 新产生的归零后果保持待生效状态 |

**起始提交阶段也不能把新产生的归零后果立即执行。** 只要效果在 K 产生，其最早生效时间就是 K+1，与产生它的系统位于 K 的哪个位置无关。

同一渲染帧可能执行多个固定 Tick；队列必须在每个固定 Tick 的边界轮换，不能等到渲染帧末尾统一轮换。暂停时不推进 Tick、请求到期或延迟效果。

### 2.2 致死伤害的明确示例

假设目标在 N Tick 开始时为 Active，当前生命 10，N Tick 命中产生 15 点伤害请求：

| Tick | 生命与状态 | 处理 |
|---|---|---|
| N | 生命仍为 10，Active | 记录伤害请求，`GeneratedTick=N`、`ExecuteTick=N+1`；不扣血、不死亡、不停机 |
| N+1 起始阶段 | 生命变为 0，正式状态仍为 Active | 结算请求；记录一次待生效归零处置，`GeneratedTick=N+1`、`EffectiveTick=N+2` |
| N+1 正常模拟 | 生命为 0，Active，同时存在待生效归零记录 | 不提前执行死亡/瘫痪，也不因检测到血量为零而提前禁止移动、开火或生产 |
| N+2 起始阶段 | 根据策略转为 Dead 或 Disabled | 提交归零转换及该阶段应有的正式控制/设备限制，输出一次死亡或瘫痪生效事件 |
| N+2 正常模拟及以后 | Dead 或 Disabled | 下游系统读取该状态，停止相应动作或生产；按各自流程处理清理、重生或维修 |

因此，**一次致死请求从产生到血量扣减延迟一个 Tick，从扣减归零到死亡/瘫痪生效再延迟一个 Tick，总计两个 Tick。** 不得将这两个边界合并为请求下一 Tick 到期时立即死亡。

这是明确接受的玩法时序：目标在生命归零后的那一个待生效 Tick 仍按原 Active 状态参与模拟。任何系统均不得通过 `Health.Current <= 0` 绕过延迟规则，提前触发后果。

### 2.3 回复、恢复和其他请求

- N Tick 的 `HealRequest`、`RepairRequest`、`RespawnRequest` 等，在 N+1 起始阶段校验并提交，不能在调用入口时直接改变正式状态。
- 普通治疗只对正常 Active 且没有待生效归零记录的目标有效，不取消已经确定的死亡/瘫痪处置。
- 建筑维修若在 K 将 Disabled 建筑生命修复为正数，由此产生的恢复资格变化最早在 K+1 提交；不能在维修结算的 K 立即恢复工作。
- 复活请求若明确包含生成新生命和初始状态，可在请求到期 Tick 完整提交其约定结果；不要额外隐式增加一层延迟。只有该次提交又产生了另一项新的正式效果时，新效果才另行遵守下一 Tick 规则。
- 延迟后果中的长流程，例如重生倒计时、维修重启计时，不要求在生效 Tick 全部完成；计时起点、完成请求和后续生效边界必须明确。

本规则约束本计划新增的生命、战斗与恢复请求。既有建造、运输等命令不会仅因本计划自动改变实现；未来接入生命相关规则时必须显式适配，不能宣称现有全部命令已经采用该协议。

## 3. 通用目标组件

以下为建议契约，实际类型名可以在实现时调整，但职责与时序必须保持。

```csharp
public struct Health : IComponentData
{
    public int Current;
    public int Maximum;
}

public enum ZeroHealthOutcome : byte
{
    Death,
    Disable
}

public struct HealthPolicy : IComponentData
{
    public ZeroHealthOutcome OnZero;
}

public enum VitalState : byte
{
    Active,
    Dead,
    Disabled
}

public struct VitalStatus : IComponentData
{
    public VitalState Value;
}
```

另需保存 `PendingVitalTransition` 一类的待生效记录，至少包含目标生命周期身份、转换原因/结果、产生 Tick、生效 Tick 和转换序号。它用于归零锁存和下一 Tick 提交，不等同于已经死亡或瘫痪的正式状态。

| 实体 | 组件组合 | 归零策略与后续处理 |
|---|---|---|
| 玩家角色 | Health、HealthPolicy、VitalStatus、玩家/生命周期身份 | Death；归零转换生效后停止控制，接入玩家死亡与后续重生 |
| 敌人/机器人 | 同一套生命组件，加单位身份和 AI/移动/武器能力 | Death；生效后停止决策、移动和攻击，再处理掉落与清理 |
| 工业建筑 | 同一套生命组件，加建筑身份、设备/生产能力 | Disable；生效后保留占格、建筑、库存与在制品，停止相应工作 |
| 可破坏装饰物，按需扩展 | 同一套生命组件，加装饰/破坏处置能力 | Death；生效后按专门流程生成残骸或移除 |

Health 不保存玩家/敌人/建筑类型，不持有行为委托、ScriptableObject 或 GameObject 回调。归零策略只描述结果，具体处置通过实体组件组合路由。

最大生命必须为 `[1, int.MaxValue]` 内的整数；当前生命必须为 `[0, Maximum]` 内的整数。不得通过普通请求隐式改变最大生命。新生成的 Active 实体应具有正生命，不能用出生即零生命绕过归零流程。

### 3.1 整数单位、计算与溢出

- `Health.Current`、`Health.Maximum`、基础伤害、`DamageSource` 的伤害值、`DamageRequest.Amount`、`HealRequest.Amount`、维修回复量和事件中的实际生命变化量统一使用 C# `int`（有符号 32 位整数）。最小单位为 1 点生命，第一版不保留小数生命。
- 定义数据、内容管理器、Baking 后的 Blob、运行时请求、结果和快照必须采用相同单位，不能出现定义为浮点数、运行时再随意截断的两套数值语义。
- 加减、累计和未来倍率计算使用 `long` 中间值，最后依据合法生命范围钳制后再写回 `int`。例如治疗使用 `min((long)Current + Amount, Maximum)`，伤害使用 `max((long)Current - Amount, 0)`；实际回复/伤害量由提交前后生命差值计算。
- 请求数值超出 `int` 范围时在输入/导入边界拒绝，不能依赖强制转换回绕。未来乘法与累计采用明确的溢出检测；超出中间表示范围时返回失败且不提交该请求的状态或物资变更，不能静默回绕。
- 若未来引入百分比修正，优先使用整数千分比：`1000` 表示 100%，非负数值按 `(long)value * multiplierPermille / 1000` 计算并向下取整。多个修正阶段的顺序和每阶段舍入位置必须固定；不通过 `float`、`double` 或平台默认舍入实现。
- 倍率结果为 0 时表示无有效变化，不隐式补成 1 点伤害/回复。基础伤害允许为 0；普通伤害和回复请求仍要求正整数，来源为 0 时不生成请求，或返回明确的无效果结果。
- Tick 编号和请求序号采用统一的整数类型与回绕规则；持续伤害、回复和维修间隔使用整数 Tick。需要表达每秒不足 60 点的持续量时，后续采用整数余数累积，不逐 Tick 将浮点小数截断而丢失总量。

整数规则只约束本计划的生命与伤害数值，不宣称 Unity Physics、位置、射线和动画时间等既有浮点计算已经改为整数。确定的请求排序、生命周期身份和固定 Tick 边界仍然必需，不能仅因改用整数就假定整个模拟已跨平台完全确定。

## 4. 定义、来源与一次请求

### 4.1 定义与来源组件

- 弹药能力的 `baseDamage` 是只读的非负整数定义参数，不保存攻击者、命中目标或当前生命。现有实现若仍为浮点字段，实施本计划时必须连同内容管理器和 Blob 一并迁移为 `int`，不能只修改生命组件。
- `DamageSource` 可挂在弹丸、陷阱、伤害区域等实际来源实体上，记录基础伤害、伤害类型及责任主体关联。
- 射线枪可以直接从枪械和弹药定义生成伤害请求，不必创建临时来源实体。
- 来源组件不会自行扣血；来源更新或触发系统只负责产生下一 Tick 的请求。

### 4.2 DamageRequest

建议至少包含：

| 字段 | 含义 |
|---|---|
| Target | 生命根实体的运行时关联 |
| TargetIdentity / LifeGeneration | 目标稳定身份及本次生命代次，防止旧请求打到复活或池化复用后的新生命 |
| Amount | 本次提交的正整数伤害，类型为 `int` |
| DamageType | 伤害类型枚举 |
| InstigatorIdentity | 责任主体，例如开枪的玩家或机器人 |
| SourceEntity | 直接来源，例如弹丸；允许为空或结算前已失效 |
| SourceItemId | 武器/物品定义来源，适用时记录 |
| SourceFactionSnapshot | 需要时记录发出攻击时的阵营信息，避免来源消失后无法判断归属 |
| RequestId | 一次请求的稳定序号，不能以 Entity 遍历顺序代替 |
| GeneratedTick / ExecuteTick | 请求产生和生效 Tick，正常为 K 与 K+1 |

实际稳定对象 ID 类型与 A01 的身份契约统一，不把 `PlayerId`、建筑定义 ID 或 `ItemContainerIdentity.RuntimeId` 混用为所有对象身份。Entity.Version 能防止销毁后实体索引复用，但同一 Entity 的重生/池化仍需要生命代次或等价版本。

**攻击者与直接来源必须分开。** 弹丸销毁、攻击者死亡不应自动撤销已经合法产生的伤害请求；结算使用提交时保存的来源信息，同时重新校验目标当前有效性和阵营规则。不要在来源已销毁后继续读取它的组件。

阵营、友伤与权限规则在请求真正生效时统一判定；源阵营采用约定的发出时快照，目标采用结算时归属。该选择需与后续基地接管规则共用，不能在每个武器系统中分别推断。

### 4.3 回复与维修请求

`HealRequest` 独立于 `DamageRequest`，使用 `int` 类型的正整数回复量；不以负伤害表示治疗。维修和复活采用明确的请求类型或操作种类，不能借普通治疗突破状态限制。

所有入口只返回请求接收情况；正式成功/失败结果在执行 Tick 结算后返回。接收成功不代表已经扣血、扣资源、修复或复活。

## 5. 唯一结算方与状态转换

建议将正式写入收敛到 `HealthResolveSystem` 或同一战斗领域内明确排序的结算模块：

1. 在 Tick 起始阶段消费本 Tick 到期的状态转换，提交 VitalStatus 及必要的正式限制。
2. 消费本 Tick 到期的生命请求，校验目标身份、生命代次、当前状态、阵营规则和数值。
3. 按稳定顺序处理每一请求，钳制生命，记录实际变化量和请求结果。
4. 首次归零时锁存待生效转换，生效 Tick 固定为当前 Tick+1。
5. 在输出阶段导出正式结果；当前 Tick 新产生的后果不能被同 Tick 下游系统直接消费执行。

其他模块不直接写 Health，不自行把 VitalStatus 改成 Dead/Disabled/Active。生成、初始化、加载或复活如需建立初始生命，必须通过明确定义的生命周期入口，而不是任意系统写字段。

### 5.1 一次归零与同 Tick 多请求

- 只有第一次从正生命结算为零时创建归零记录，同一生命代次最多存在一个待生效归零转换。
- 归零锁存后，到转换生效前，额外普通伤害和治疗均返回明确的目标状态不允许结果，不重复触发归零，也不通过治疗撤销后果。
- 请求按约定的稳定排序键处理，例如 `ExecuteTick、SourceStableId、RequestSequence`；需要统一伤害与回复的相对顺序。并行 Job 的完成顺序、Entity 索引、ECB 的偶然追加顺序不能成为玩法规则。
- 不将同 Tick 的总伤害与总治疗简单相抵。先治疗再受致死伤害，与先致死再治疗，结果可不同，但必须由稳定排序得到。
- 到期转换先于到期请求处理。因此同一 Tick 发生归零转换与普通治疗到期时，先进入 Dead/Disabled，普通治疗不能“抢先救回”。

### 5.2 不同的正式后果

在归零效果的生效 Tick，根据组件组合执行：

```text
Dead + 玩家身份       → 玩家死亡处理
Dead + 机器人身份     → 单位死亡处理
Disabled + 建筑身份   → 建筑瘫痪处理
```

正式控制/决策/生产限制必须在该 Tick 的正常模拟开始前可见。必要时通过 VitalStatus 作为统一条件立即供下游查询，再在约定结构变更屏障提交停用标记；不能等到该 Tick 末尾才回放 ECB，让对象多行动一次。

后果处理采用待处理标记、转换序号或消费记录保证一次性。物资掉落、清理、奖励和重生安排均不得因多个渲染帧读取 Dead 而重复执行。

战斗领域可以拆成生命结算、玩家死亡、机器人死亡和设备瘫痪等系统，不要求一个巨型系统管理所有领域。设备模块负责设备工作条件，库存模块负责物资事务，战役/恢复模块负责重生地点与恢复规则。

## 6. 治疗、瘫痪恢复与物资事务

1. 普通治疗只作用于允许治疗的 Active 生命；Dead 只能通过明确复活/重生流程恢复。
2. Disabled 建筑由维修请求修复，不能由普通治疗隐式恢复工作。
3. 维修扣除修补件与增加生命在请求到期 Tick 的同一受控事务中提交。条件不满足、目标过期或库存不足时，两者均不提交。
4. 请求产生时不先扣维修材料，再等待下一 Tick 判断是否修复。若未来加入预约，预约与实际扣除必须区别保存，失败释放预约。
5. 维修产生的重新激活效果仍延迟到下一 Tick；生效前重新检查生命和恢复资格。重新激活与后续重启流程按 B01 的规则定义。
6. 设备能否工作由未瘫痪、供电和其他条件共同决定。恢复生命或解除瘫痪不清除断电、缺料、权限不足等独立原因。
7. 瘫痪保留建筑、布局、库存和在制品；传送带等设备是否纳入受损范围由 B01 收敛，不默认所有实体都可受损。

## 7. 目标定位、物理与生命周期

- Health 挂在逻辑根实体上；碰撞子实体通过 `DamageTargetOwner` 或等价关联映射到生命根实体。
- 多个碰撞体命中同一目标时，按攻击语义去重。一次爆炸对同一生命根实体通常只生成一份伤害请求，不能按碰撞体数量重复扣血。
- 没有 Health 不代表没有遮挡。不可损坏墙体仍可阻挡射线，命中检测和可受伤判断是两个步骤。
- 查询使用 ECS 实际物理世界，不默认 GameObject 射线能命中 ECS 碰撞体。
- 移动与命中使用的物理快照在 A02/A04 明确；命中结果只生成下一 Tick 请求，不即时改写目标。
- 目标在生效前拆除、销毁、换代或重生时，旧请求及旧归零转换均应被拒绝/丢弃，并留下可诊断结果，不影响新生命。
- 死亡后的碰撞体退休与释放复用现有生命周期边界，检查 `EcsCharacterMotor` 和 `RetiredCharacterColliderCleanupSystem`，避免重复销毁、提前释放仍被物理世界使用的 Collider Blob。

## 8. 系统分组、队列与事件

### 8.1 固定 Tick 集成

正式生命、伤害、回复、归零转换、持续伤害、回血/维修计时均纳入固定 Tick。后续射速、换弹等战斗状态也沿用固定 Tick。

当前 `Stage3FixedRateSystem` 在初始化阶段设置 60 Tick/s；角色更新位于 `KinematicCharacterPhysicsUpdateGroup`，生产位于 `FixedStepSimulationSystemGroup`。应在固定模拟中建立清楚的战斗起始提交阶段和请求生成阶段，并对照现有组层级安排顺序。

不得随意移动现有物理、生产、运输系统；不得对不同父组下的系统简单添加 `UpdateAfter` 就认为顺序已被保证。只要所有下游系统在 K 正常模拟阶段读到 K 起始已提交状态，其他领域内部顺序可以保持现状。

### 8.2 请求与转换队列

- 使用 current/next 队列或按 ExecuteTick 分桶的有界结构，实现下一 Tick 语义。current 在 K 起始封闭，任何 K 产生的请求都不能追加回 current。
- 归零转换单独记录到期 Tick，不能在伤害处理后扫描全部零生命并立即执行。
- 桥接输入在统一 Tick 入口封口后归属当前 Tick。渲染帧采集到的意图由入口分配 GeneratedTick，不能按某个 MonoBehaviour 调用恰好早晚改变生效时机。
- 生产者 Job 写 next；轮换和消费前完成必要依赖，不让尚未完成的写入跨越队列边界。
- 请求消费后清理，旧 Tick 不无限重放。重复提交以请求身份防止重复结算；范围伤害的身份需包含目标，不能把一个爆炸对多个合法目标误判为重复。
- 短期去重记录必须有明确生命周期；当前单机范围不建立无限增长的全局历史集合。
- 世界重开清理全部请求、待生效转换、事件和序号上下文，避免上一局伤害影响新世界。

### 8.3 正式结果与表现

HealthChanged、Death、Disabled 等事件明确区分产生 Tick 与已生效 Tick。死亡/瘫痪事件只在转换正式生效时对外发布；待生效归零记录属于内部正式调度数据，不能伪装为已死亡事件。

正式后果不依赖音效或动画消费者，不能由表现层读事件后决定扣血、死亡、停机或发放掉落。HUD、动画、相机和音效在渲染帧读取已提交快照和事件；视觉反馈可以在其看到结果的渲染帧播放，不反向改变 Tick 语义。

一帧内多个固定 Tick 的事件必须完整导出并按序消费；一次事件不能跨渲染帧重复播放。事件序号、消费边界和保存时长沿用现有桥接原则，不长期保留全部历史。

## 9. 内容工具与代码落点

建议目录：

```text
Assets/Scripts/
  DataBase/Definitions/          最大生命、归零策略等创作定义，按实际需要增加
  DataBase/Validation/           生命、来源和引用校验
  ECS/Data/Combat/               Health、VitalStatus、请求、待生效转换与结果
  ECS/Systems/Combat/            固定 Tick 结算及归零转换
  ECS/Authoring/                 角色/建筑创作与 Baker 接入
  ECS/Presentation/Bridge/       生命快照和已生效事件出口
Assets/Tests/                    规则、时序与阶段接入回归
```

最大生命、归零策略属于定义；当前生命、生命代次、待生效转换和冷却属于 ECS 运行状态。物品的枪械/弹药能力继续作为来源规格，不能将建筑或角色生命塞入物品能力组件。

定义接入现有领域内容库与内容管理器。尚无真实需求时，不增加通用回调注册表、通用效果图、复杂抗性表或第二套数据源。

## 11. 验收清单

### 11.1 必须通过的时序用例

- [ ] N 产生伤害，N 内生命不变；N+1 起始才扣血。
- [ ] N+1 扣血归零，N+1 内不死亡/瘫痪；N+2 起始才改变正式状态与行为限制。
- [ ] 待生效归零 Tick 中，移动/开火/生产不会仅凭零生命提前停下；生效 Tick 不额外多行动一次。
- [ ] 起始阶段产生的新效果也必须等下一 Tick，不能因位于队列消费者之前而当 Tick 生效。
- [ ] 同一渲染帧执行多个 Tick，与多个渲染帧各执行一个 Tick 的正式结果相同。
- [ ] 暂停、恢复不会按墙钟时间跳过请求或提前完成转换。
- [ ] 下一 Tick 到期转换先于到期生命请求；普通治疗无法撤销已经锁存的归零处置。
- [ ] 建筑维修增加生命与恢复工作之间遵守下一 Tick 规则，恢复不清除断电等独立状态。

### 11.2 正确性与生命周期

- [ ] 玩家、机器人、建筑使用相同生命结算，归零结果分别路由至正确后果。
- [ ] 同 Tick 多次致死请求、重复提交和多渲染帧读取不会重复死亡、瘫痪、掉落或奖励。
- [ ] 定义、内容管理器、Blob、请求、结果和快照的生命/伤害/回复字段统一为 `int`，不残留每次结算时的浮点转换。
- [ ] 非整数、超范围、负数请求、零值请求和非法最大生命等输入按契约拒绝；浮点旧数据入口若存在，NaN/Infinity 同样拒绝。基础伤害为零与请求为零的处理区别明确。
- [ ] `int.MaxValue` 附近的治疗、伤害和累计使用宽整数中间值，不溢出回绕；提交后的生命始终位于合法范围。
- [ ] 若引入整数倍率，覆盖千分比舍入、多个修正阶段的固定顺序、零结果及溢出失败不部分提交。
- [ ] 伤害与回复采用稳定顺序，普通治疗不能复活；失败原因可被调用方识别。
- [ ] 来源先销毁仍能按保存的合法来源信息结算；目标销毁、拆除或生命代次变化则拒绝旧请求和旧归零转换。
- [ ] 多碰撞体映射至同一生命根实体；单次范围攻击不会重复扣血，不可损坏遮挡仍然有效。
- [ ] 阵营变化后的判断符合统一快照/结算规则，不由不同武器自行处理。
- [ ] 维修失败不扣料，成功时扣料与加生命一致提交；瘫痪/恢复不复制库存或在制品。
- [ ] 世界重开没有残留请求、事件、归零记录或旧角色碰撞引用。

### 11.3 工程回归

- [ ] 先运行新增生命和时序专项测试，再运行完整 `Factory.Tests`。
- [ ] 涉及玩家、物理、生命周期、UI 或动画适配时，运行相关及完整 `Factory.PlayModeTests`。
- [ ] 核对系统组、物理快照、ECB 屏障和队列轮换位置，并在实际实现记录中写清。
- [ ] 记录实际规则、关联代码、测试日志和剩余问题；未经专项授权，不扩展为大规模压力测试。

## 12. 计划的强制解释

本计划不保留“可选择本 Tick 或下一 Tick”的实现自由。统一采用：

> **请求在产生后的下一 Tick 结算；结算新产生的生命归零后果再在下一 Tick 生效。当前 Tick 只能产生下一 Tick 的工作，不能立即执行新产生的正式效果。**

后续若确需改变这项规则，必须先修改本计划、相关调用契约和时序测试，不能由某个系统局部采用立即结算。
